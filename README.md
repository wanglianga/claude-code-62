# 县殡仪服务预约与治丧物品结算平台

> Vue 3 + Spring Boot 3 + PostgreSQL，Docker Compose 一键部署。
> 围绕**同一张治丧单**串联：家属预约 → 五要素核验 → 方案沟通与逐次签字 → 跨岗位协同 → 三类费用结算 → 服务归档回溯。

---

## 原始需求 / 原始 Prompt

建设县城殡仪服务预约与治丧物品结算平台，可采用 Vue 3、Spring Boot 和 PostgreSQL。家属提交逝者信息、死亡证明、接运地点、宗教习俗、是否需要冷藏、告别厅规格和亲属联系人后，平台先核验证件、接运车辆、馆内冷藏位、火化排期和可用礼厅。业务员沟通治丧方案时，要把遗体接运、化妆、告别仪式、花圈挽联、寿衣、骨灰盒、餐饮、休息室和减免政策放在同一订单里说明；家属每次确认或删减项目都要保留签字记录。若逝者来自外地、亲属意见不一致、证明材料缺失、低保减免待审核、告别厅临时冲突或火化设备检修，平台要让接运组、业务员、财务、礼厅管理员和馆领导围绕同一治丧单处理。服务结束后，费用明细、减免依据、火化证明、骨灰领取人、未结项目和家属反馈进入档案，后续有费用争议或证件补办时可以回到原始服务过程。平台还要区分公益基本服务、自选增值服务和政府补助项目，费用单必须让家属看到每一项的来源、确认人和是否可退。遇到亲属情绪激动或现场临时增减仪式时，业务员需要先保存沟通记录，再变更礼厅、车辆和物品库存，避免结算时出现口头承诺争议。

## 一、需求落地说明（逐条对照）

| 原始需求 | 平台实现 |
| --- | --- |
| 家属提交逝者信息、死亡证明、接运地点、宗教习俗、冷藏、厅规格、联系人 | 「新建预约」表单完整覆盖；证明可选「材料缺失」先登记后补办；外地勾选后自动发起接运组协同 |
| 先核验证件、接运车辆、馆内冷藏位、火化排期、可用礼厅 | 治丧单「① 资源核验」一次性核验五要素；按时间段检测冲突，检修资源自动停用；未通过时给出**可替代资源**并自动向责任岗位发起协同、预占资源 |
| 九类治丧内容与减免政策放在**同一订单**说明 | 「② 治丧方案」同一订单条目：遗体接运/化妆整容/告别仪式/花圈挽联/寿衣/骨灰盒/餐饮/休息室，补助项目入同一订单以负额冲减 |
| 家属每次确认或删减项目都保留签字记录 | 前端 Canvas **手写签名板**（PNG 入库存证）；逐项确认、逐项删减、确认整体方案、确认费用、骨灰领取均强制签字；已确认物品删减时自动退回库存 |
| 六类异常下五岗位围绕同一治丧单处理 | 「④ 跨岗位协同」+ 协同中心：材料缺失/亲属分歧/减免待审/礼厅冲突/设备检修/外地逝者，自动派单到接运组、业务员、财务、礼厅管理员、馆领导，处理结果回填闭环 |
| 先保存沟通记录，再变更礼厅、车辆和物品库存 | 「③ 沟通与现场变更」：情绪激动/意见分歧/临时变更类记录**保存即锁定**；服务进行中增删物品或变更资源必须引用锁定的沟通记录，否则后端拒绝；杜绝口头承诺 |
| 区分公益基本/自选增值/政府补助；费用单展示来源、确认人、是否可退 | 费用单三类分组、不同颜色标识；每行展示**来源/定价依据、确认人、可退标识**；减免单列减免依据 |
| 费用明细、减免依据、火化证明、骨灰领取人、未结项目、家属反馈入档案 | 「⑥ 完成/领取/归档」：结清后正式归档生成档案快照；服务档案页可检索 |
| 费用争议或证件补办可回到原始服务过程 | 每张治丧单保留全程**时间线留痕**（提交/核验/沟通/签字/变更/协同/减免/结算/领取/反馈/归档），归档后仍可一键回溯 |
| **困难家庭减免两级审核** | 家属申请低保/特困/临时救助减免时登记**证明材料、社区（村/居）联系人、申请减免项目**；**财务初审 → 馆领导终审确认**，两级意见与依据全程留痕 |
| **审核期间基础服务继续、高价/额外仪式二次确认** | 减免审核中公益基本服务（接运/冷藏/火化等）照常预约推进；单价≥500元或告别布置、花圈挽联、餐饮、休息室等高价用品/额外仪式自动加守卫，需家属**二次手写签字**，否则不能随方案确认、不能开始服务 |
| **费用单三分类 + 调整差额提示** | 终审通过后费用单区分**已减免（政府补助负额）、仍需自费、不可减免/减免范围**；家属调整用品时实时显示相对批准基线的**新增自费差额** |
| **补选不自动扩大减免** | 终审后补选的用品标记「减免后补选」，列入不可减免；确需追加须**重新提交申请并再次经财务初审、馆领导确认**；扩大申请被驳回时原已批准减免继续有效 |

## 二、技术架构

```
浏览器 ──HTTP──> frontend (nginx:8080, 静态页 + 反代 /api)
                      │ docker 内网
                      └──> backend (Spring Boot 3 / JDK17 :8080)
                                │
                                └──> db (PostgreSQL 16 :5432，不发布宿主)
```

- 前端：Vue 3（`<script setup>`）+ Vite 6，无额外 UI 框架，Canvas 原生手写签名。
- 后端：Spring Boot 3.3、Spring Data JPA、Hibernate 自动建表、Actuator 健康检查、BCrypt 口令；
  轻量 Token 认证（`X-Auth-Token` 头）+ 拦截器注入当前操作人，所有写操作自动进入时间线。
- 数据库：PostgreSQL 16，数据卷 `pgdata` 持久化；首次启动自动建表并写入演示账号、服务目录、馆内资源。
- 资源冲突：`resource_booking` 时间段重叠判定（车辆/冷藏位/礼厅/火化炉），支持预占、改期自动释放。
- 库存：寿衣、骨灰盒、花圈等物品确认签字时扣减，删减时回退；库存不足阻断确认。

## 三、一键启动（验证方式 = 宿主 docker compose up）

前置：宿主已安装 Docker 与 Compose 插件；`DOCKER_HOST` 已指向宿主 daemon；
应用宿主端口通过环境变量 **`CC_PUBLISH_PORT`** 指定（并行任务不冲突）。

```bash
cd /workspace
cp .env.example .env          # 可按需修改 CC_PUBLISH_PORT / 数据库口令
docker compose up -d --build  # 构建并启动 db / backend / frontend 三个服务

# 查看实际映射端口（不要硬编码 3000/8080）
docker compose port frontend 8080
# 健康检查（容器内 actuator；外部经 nginx 代理）
curl -fsS "http://host.docker.internal:${CC_PUBLISH_PORT}/api/auth/me" -i   # 未带 token 返回 401 属正常
```

浏览器打开：`http://<宿主IP>:<CC_PUBLISH_PORT>`（本任务示例 `http://host.docker.internal:3062`）。

停止与清理：

```bash
docker compose down          # 停止并移除容器（保留数据卷）
docker compose down -v       # 连同演示数据库一并删除
```

镜像均为**多阶段构建**：Maven 构建 → JRE 运行；Node 构建 → nginx 运行；运行容器使用非 root 用户并配置了 `HEALTHCHECK`。

  其中 **3 号火化炉初始即为「检修中」**，可直接演示「火化设备检修」协同与替代设备推荐。

## 五、建议走查路径（关键业务流，约 8 分钟）

1. **家属 `family` 登录 → 新建预约**：填写逝者/接运地点/联系人，勾选「需要冷藏」「外地」，证明状态选「材料缺失」，提交。
   系统自动生成单号并产生「外地逝者」「材料缺失」两条协同。
2. **业务员 `clerk` 登录** 打开该单 → 「① 资源核验」：选择车辆、冷藏位、礼厅（注意规格匹配提示）、火化时间；
   若故意选择检修中的 3 号炉，会得到红色未通过项、替代炉推荐并自动生成「设备检修」协同；换 1/2 号炉后核验通过并预占。
3. 「② 治丧方案」：从三类目录加入接运、化妆、告别布置、花圈挽联、寿衣、骨灰盒、餐饮、休息室；
   切回家属 `family` 逐项**手写签字确认**（体验删减也要签字、库存自动变化）。
4. 「③ 沟通与现场变更」：登记一条「现场临时变更」（保存即锁定）→ 凭该记录更换礼厅/车辆，系统重新核验并在记录上标注「已据此变更」；
   未选锁定记录直接在服务中加项会被后端拒绝。
5. 「④ 跨岗位协同」：分别用接运组、礼厅管理员、馆领导登录协同中心处理待办并回填结果；
   登记「亲属意见不一致」沟通会自动给馆领导派单。
6. 家属签字确认整体方案 → 业务员「开始服务」→「服务完成」填写火化证明编号。
7. 「⑤ 费用与结算」：家属点「提交困难家庭减免申请」，选择低保/特困/临时救助，填写证明材料、社区联系人并勾选申请减免项目
   → 财务 `finance` 初审（可电话核实社区，填写初审意见，通过转馆领导）→ 馆领导 `leader` 勾选批准的政府补助项目与减免范围、填写依据终审；
   审核期间可继续用 `clerk` 添加基础服务，而加入「告别仪式隆重布置/花圈/餐饮」等会自动打上「待二次确认」，
   必须由家属 `family` 二次签字，否则开始服务会被系统拦截。终审通过后费用单分**已减免 / 仍需自费 / 不可减免**三段展示。
8. **差额与补选**：终审后家属再补选（如玉石骨灰盒），条目标记「减免后补选」，费用单顶部提示新增自费差额，减免范围不自动扩大；
   家属可重新提交减免申请（再次走两级审核），若馆领导驳回扩大范围，原补助仍有效、补选全额自费。
9. 家属签字确认费用 → 财务收款（未签字时收款被系统阻止）→ 结清。
10. 「⑥」骨灰领取人签字、家属星级反馈 → 财务正式归档 → 在「服务档案」中可检索并打开该单，
    查看费用快照、减免依据（含两次审核意见）、火化证明、领取人、未结项目与完整时间线，模拟费用争议/证件补办回溯。
